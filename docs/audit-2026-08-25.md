# Repo Audit & Deep-Research Comparison — 2026-08-25

A four-agent audit of the whole repo (split: scrape stack / agent hierarchy & prompts /
run pipeline & reporting / tests & CI), triggered by the failed 1800s run
`20260825134545 — "can you find me cool selfhosted services…"`, which ended with ~110
provenance-rejected fetches, one researcher dead on `APITimeoutError`, and a published
report whose `## Answer` was the lead's planning preamble. Plus research on how
production deep-research systems (Claude Research and peers) scrape hundreds of sites
in ~15 minutes, and what of that transfers here.

Every finding below was verified against the code by the auditing agent before being
reported (files and line numbers are as of this commit's parent).

---

## 1. Executive summary — why the harness is slow and scrapes so few sources

The failed run was not one bug; it was five mechanisms compounding. Ranked by impact:

1. **The provenance rule is invisible to the model (dominant).** `fetch.py` enforces
   "only URLs from `search_web` results (or user-pasted) are fetchable," but no prompt
   (`orchestrator.md`, `subagent.md`, `reader.md`) and no tool description ever states
   it, and every rejection renders the same deliberately opaque per-URL line as a guard
   block ("do not retry this URL"). A researcher holding canonical URLs from prior
   knowledge learns nothing generalizable and guesses fresh URLs one rejection at a
   time — ~110 times, all run, for near-zero pages scraped. The opacity rationale (D1:
   don't tell an adversarial page which guard signal fired) does not apply to
   provenance, by `_provenance_rejected_detail`'s own docstring.

2. **The guard silently shrinks the source pool.** Verified by execution: `system:`
   YAML keys, `[system]` INI/TOML headers, `System: Ubuntu 22.04` spec lines, and links
   with `?apikey=`/`?metadata=` query params all fire the injection-guard regexes,
   which drop the whole page or search result with only a RunLog incident. For
   config-heavy topics — self-hosted services being the worst case — this removes many
   of the best sources invisibly. The benign test fixtures are all prose articles, so
   this false-positive class is unmeasured.

3. **Throughput is capped by hardcoded literals and a shared 5-connection pool.**
   "Up to 3" concurrent researchers and "about 4 searches" live as prompt prose, not
   config; the Reflection section nudges the lead back to serial dispatch. The warm
   HTTP crawler — the cheap pass meant to carry most pages — shares ONE
   `max_connections=5` pool across all researchers, while the expensive browser path
   gets a fresh 5-permit dispatcher per call. The `MemoryAdaptiveDispatcher`'s 75%
   threshold is hardcoded and measured against whole-system memory on a box that also
   runs SearXNG and a resident Chromium, so it can throttle every batch all run.

4. **Retry/timeout amplification.** One global 120s non-streaming timeout for all four
   roles × SDK `max_retries=2` means a single slow model call burns ~6 minutes; the
   task-tool retry then replays the entire researcher subagent on ANY failure —
   including deterministic ones (context-length 400s, reachable because the 200k
   summarization trigger ignores the configured model's window). One bad dispatch can
   cost 10+ minutes of an 1800s budget. This matches the observed `APITimeoutError`
   researcher death.

5. **The synthesis reserve can never fire on the runs it exists for.** The margin check
   runs only on top-level stream chunks, but one researcher dispatch is one superstep —
   no chunk arrives for minutes. If the margin trips mid-dispatch (the normal case on a
   slow run), the run rides straight into the hard wall clock answerless. Then
   `_final_answer` accepts the planning preamble (prose on a tool-calling AIMessage) as
   the "final answer," so a garbage report ships and the run exits 0 — defeating the
   no-report-on-answerless-expiry invariant.

Post-run latency is a separate sink: verification is strictly sequential, one model
call per paragraph, each re-uploading the complete untruncated capture of every cited
source, plus a consolidation call that runs even when zero model checks happened.
Startup adds four serial model preflights + search preflight + browser launch.

## 2. How production deep-research systems scrape 100s of sites in ~15 minutes

Research sources: [Anthropic's engineering post (via Simon Willison)](https://simonwillison.net/2025/Jun/14/multi-agent-research-system/),
[ByteByteGo breakdown](https://blog.bytebytego.com/p/how-anthropic-built-a-multi-agent),
[The AI Engineer breakdown](https://theaiengineer.substack.com/p/how-anthropic-built-multi-agent-deep),
[ZenML LLMOps case study](https://www.zenml.io/llmops-database/building-a-multi-agent-research-system-for-complex-information-tasks),
[LangChain: context management for deep agents](https://www.langchain.com/blog/context-management-for-deepagents),
[Brave: search APIs vs scrapers](https://brave.com/learn/best-search-api-2026/),
[aimultiple agentic-search benchmark](https://aimultiple.com/agentic-search),
[Exa vs Tavily](https://exa.ai/versus/tavily).

**Double parallelism.** Claude Research is an orchestrator-worker system: the lead
spawns **3–5 subagents in parallel, and each subagent issues 3+ tool calls in
parallel** within a single turn. That double fan-out cut research time on complex
queries by up to 90%; at peak the system ingests 50–60 pages simultaneously. Token
throughput is the point — token spend explains ~80% of performance variance on hard
research (BrowseComp), at ~15× the tokens of a normal chat.

**No per-page browser.** The biggest structural speed gap: production systems read
from search/index APIs (Brave/Exa/Tavily-style) that return pre-processed, pre-rendered
page content in milliseconds, instead of booting a browser navigation per URL ("a
scraper API boots a headless browser per request, adding seconds of latency"). This
harness's HTTP-first pass is the right instinct; the browser escalation path and the
run-wide 5-connection HTTP pool are where the seconds go.

**Aggressive compression.** Subagents return condensed findings, not raw pages; raw
pages are summarized by a small cheap model and only summaries reach the lead (~47%
cost reduction, negligible quality loss in one study); large tool results are offloaded
to a filesystem/memory store. The reader-digest design here matches this pattern — but
the failed run shows most sources falling back to "read raw," which defeats it.

**Effort scaling is taught explicitly.** The lead is prompted with scaling rules
(simple lookup → one subagent, a few calls; broad survey → full fan-out) and each
subagent gets a precise goal, source constraints, and a page-read budget. Delegation
quality, not politeness of sequencing, is the tuned variable.

**Citations are one cheap post-pass**, not per-claim model calls — contrast with this
harness's one-verifier-call-per-paragraph tail.

**What transfers here, in order of leverage:** state the fetch contract in the prompts
(free), raise and config-drive researcher parallelism and search budgets, widen the
HTTP pool so the cheap pass actually fans out, make the reader digest the default path
that works, and turn verification into batched/concurrent calls.

## 4. Suggested fix order

Highest payoff per line changed, respecting the invariants (no shell tool, config-driven
routing, best-effort + disclose):

1. **Prompt + tool-contract fixes for provenance** (3.2 row 1) — a few sentences; would
   have saved most of the failed run's 1800s on its own.
2. **`_final_answer` skips tool-calling messages + regression test** (3.1 rows 1, 3.4
   row 1) — restores the no-report-on-answerless-expiry invariant.
3. **Time-driven synthesis margin** (3.1 row 2) — converts slow-but-salvageable runs
   into answered ones.
4. **Guard regex tightening + benign config-page fixtures** (3.1 row 3) — recovers the
   silently dropped source pool.
5. **Search timeout knob, filter-before-slice, approval-key widening** (3.1 row 5, 3.2
   rows 4–5) — cheap, all config/ordering changes.
6. **Throughput config: parallel researchers, search budget, HTTP pool, memory
   threshold; narrow task retry; per-role timeouts** (3.2 rows 2–3, 6–8).
7. **Verification concurrency/batching + consolidation gate** (3.2 rows 9, 12) — cuts
   the post-run tail.
8. **CI security hardening + branch coverage + dev-dep pins** (3.3, 3.4 row 3, 3.5
   row 9).
9. Test consolidation and cleanup items as they're touched (3.5, 3.6).
